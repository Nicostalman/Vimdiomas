> Also settled at sprint start: warnings are **surfaced, never blocking**.

> **Deliverable.**
>

**The milestone does two things** (the dev, 2026-10-02, settling the good-faith

> 2. check if, inside that sanitized format, there are changes and update

So the check is **a rule, not a list of cases**: the format the app generates is

second half: a conforming file's changes are read back and acted on.

What earlier milestones left for this one (sprint notes):

- **M2:** a warning quoting a raw line from a file goes through
  `base.literal()` — that line is exactly the kind of text that holds brackets.
- **M3:** parse warnings reuse `CompileReport.warnings` /
  `CompileWarning(source, message)` rather than a second channel. Compile
  warnings are reported for **every** file on every Compile, rebuilt or not.
- **M4:** every Compile re-parses every file; only xelatex is skipped for an

## 1. The autogenerated format

The format is defined by `writer.write()` — the only thing in the app that
produces a file — and this is the spec of what it emits. `N` is the kind's
column count: **3** for a kind with a reading (Chinese: `word`, `reading`,
`translation`), **2** for one without (German and every alphabetical language:
`word`, `translation`).

```
# <title>                         the filename's stem, first line, exactly once
<blank>
<entry row>…                      uncategorized entries, if any
<blank>
## <category name>                zero or more, each name unique in the file
<blank>
<entry row>…
<blank>
### <subtitle name>               grammar files only; unique within the category
<blank>
<entry row>…
<blank>
## Tags                           at most once, last, only if there are tags
<blank>
#tag #tag …                       one line, space-separated, shlex-quoted
```

- **An entry row** is exactly `N` tab-separated fields. `word` is never empty
  (Entry's Create is a no-op without one); `reading` and `translation` may be
  (M1: an empty translation is a legitimate row). No field contains a tab or a
  newline (M1, #15).
- **A note** is the line directly after its entry row: four spaces, then the
  note wrapped in `*`.
- The file ends with exactly one newline, and no blank line before it.

Nothing else is ever written. In particular the app never writes a fourth
column, a `####` heading, a markdown table, a line of prose, a second `## Tags`,
a duplicate category name, or a tag block token that is not a `#tag`.

## 2. Anything outside it is reported

**The rule.** A file is checked against §1, and a deviation is **reported** when
it is *lossy* — when the text does not reach the compiled PDF as itself, or is
read back as something other than what it says. A deviation that is *lossless* —
read back faithfully, and tidied by the next in-app write — is **not** reported.
That is the "sanitize the file for compiling" line: what is reported is exactly
what would otherwise be missing from, or wrong in, the PDF.

Both tables below are derived from that rule against §1's grammar, and they are
exhaustive as of this milestone. A later change to the format extends them by
the same rule rather than by taste.

### Reported

| Deviation | What it does today | Status |
| --- | --- | --- |
| A line matching no line type of §1 — a markdown table, a line of prose, YAML front matter, `#### `, `## ` with no name, `### ` in a vocabulary file, `### ` outside a category, a `*note*` line not following an entry row | Dropped from the deck; absent from the PDF | **Already warns** (`unrecognized line`) |
| An entry row with fewer than `N` fields | Dropped from the deck | **Already warns** (`unrecognized line` / `malformed entry row`) |
| An entry row with **more** than `N` fields, where an extra field has content | Kept on disk in `Entry.extra_fields`, **never rendered** — the text is on disk and missing from the PDF | **New**: `extra column(s) never rendered: <fields>` |
| An entry row whose **word** is empty | Renders a blank first column; Entry cannot create one | **New**: `an entry with no word` |
| A token in the tag block that is not a `#tag` — prose under `## Tags`, an entry row after it, or a multi-word tag written unquoted (`#C1 exam`) | Each word silently becomes a tag: an entry row after `## Tags` disappears from the deck into four tags, and `#C1 exam` becomes `C1` and `exam` | **New**: `not a tag: <tokens>` |
| A second `## Tags` heading | Everything under it is read as tags; a category by that name is unreachable (M1 refuses creating one in the app) | **New**: `the tag block appears more than once` |
| Unparseable tag quoting | The file's whole tag block is lost | **Already warns** (`unparseable tag syntax`) |
| A `# ` header that is not the filename's stem | pandoc titles the PDF from the filename, so the header is not what the PDF says | **Already warns** (`header '<x>' does not match filename '<y>'`) |
| **No** `# ` header line at all | Parses, titles from the filename — the one structural element the app always writes, missing | **New**: `no '# <stem>' header line` |
| A category name appearing twice in a file | Both render; the app's tree lists the name twice, and a create writes into the first, so the second is unreachable from the app | **New**: `category '<name>' appears more than once` |
| A subtitle name appearing twice in a category | Same, and creating a duplicate subtitle in the app selects the existing one instead | **New**: `subtitle '<name>' appears more than once` |

### Not reported

Lossless: the deck is exactly what the text says, and the next in-app write
tidies the file into §1's shape. Warning on these would be noise on a file that
is, in every sense that matters, correct.

| Deviation | Why it is not a warning |
| --- | --- |
| Blank-line runs, missing or extra blank lines, no trailing newline | Whitespace between blocks carries nothing; normalized on the next write |
| A note indented by other than four spaces, or by a tab | Read back identically; re-indented on the next write |
| `## Tags` placed before the categories, or an empty `## Tags` section | Read back identically; moved or dropped on the next write |
| Tag order, and a tag quoted where the writer would not have quoted it | `shlex` reads both; rewritten in the writer's form |
| A `# ` header that matches the filename but is not the first line | Read as the header, PDF unchanged; moved to the top on the next write |
| A trailing tab producing one **empty** extra field | Nothing is lost — there is no text to lose. A non-empty extra field is reported above |
| An entry with an empty `reading` or `translation` | M1 settled this as a legitimate row: "hanzi remains the single required field" |
| A duplicate **entry** (the same word twice) | Two identical rows render as two rows. The app can create them too |

### Where the check lives

All of it in `parser.parse()`, which already walks the file line by line and
already owns `models.Warning(line_number, message, raw_line)`. No second module
and no second pass: the parser is the one thing that knows what it did with each
line, and the file-level checks (a missing header, a duplicate name, a second
tag block) need only what it already tracks. Every surface then stops
discarding what it returns.

A file-level warning with no single line to blame (`no '# <stem>' header line`)
reports `line_number = 0` and an empty `raw_line`; the surfaces render it
without a line number.

## 3. Changes inside the format: trivial and non-trivial

The dev's points 3 and 4. Among the lines that respect §1, a hand change is:

- **Trivial** when it changes nothing at the TUI level — a translation, a
  reading, a note, the order of words inside a category or between categories,
  the order of the categories themselves. The TUI shows files and category
  names; none of these is either.
- **Non-trivial** when the TUI shows it — a category renamed, added or removed;
  in a grammar file, a subtitle renamed, added or removed; a file's uncategorized
  block appearing or emptying, which is a leaf in Entry's tree.

Both reach the PDF; only the non-trivial ones have anything to update on screen.

| Hand change inside the format | Kind | What must reflect it |
| --- | --- | --- |
| A category renamed, added or removed | Non-trivial | Entry's tree and its create target; the PDF's heading on the next Compile |
| A subtitle renamed, added or removed (grammar) | Non-trivial | Entry's subtitle field for that category; the PDF |
| A file's first uncategorized entry added, or its last removed | Non-trivial | `FileNode.has_uncategorized`, and so Entry's `(uncategorized)` leaf |
| An entry moved between categories or files, or reordered | Trivial | The deck's order, so the PDF's row order |
| Categories reordered | Trivial | The PDF's section order |
| A word, reading, translation or note edited | Trivial | The PDF's cell |
| A tag added, removed or renamed | Trivial | Browse's tag filter (`store.tag_index`, mtime-keyed), which rebuilds on open |
| A file renamed by hand | — | The header check of §2 reports the mismatch it causes |

**Settled with the dev:** the app does **not** work out which it was. On the
re-read of §4 the TUI is rebuilt from the file unconditionally — the tree, the
marker, the preview, the PDF — so a non-trivial change is always reflected, and
a trivial one costs a rebuild that redraws the same thing, which is precisely
what makes it trivial. No before/after deck is kept and no differ is written.
The rejected alternative named the change in a notification ("Fruits renamed to
Obst") at the cost of a differ over names, order and fields, and wording rules
for several changes at once.

This works because nothing in the app holds a category name, an entry or a tag
across a read: every screen derives its state from the file each time. Verified
rather than assumed — `compile.py`'s staleness cache is keyed on the rendered
markdown (M3, #11), `store.TagCache` on mtime, `pdf_preview.RasterCache` on the
PDF's mtime. There is no stale state for a hand edit to get stuck behind.

## 4. When the app reads the file

**Settled with the dev:** the app does not watch the tree. "If the user
modifies the file through the terminal manually, then the program won't notice.
If the user then enters through the md mode to the same file, and just exits,
then the program will notice and raise a warning."

So there is **no watcher, no polling, and no re-read on screen resume**. The
check runs where the app reads the file anyway:

| Moment | What is read | What it produces |
| --- | --- | --- |
| A tree screen is opened (Entry, Inspect Tree) | Every `.md` under the tree root, once | The trees, with the marker of §5 |
| **MD mode's `nvim` exits having changed the file** | That file | The tree is rebuilt, the preview refreshed, the PDF recompiled, and a notification gives the warning count |
| Entry creates an entry or a category | That file | The hand edits are kept — Entry re-reads before every write |
| Compile, and `idiomas compile` | Every `.md`, parsed and re-rendered whatever the stamp says (M4) | The PDFs, and the warnings of §6 |
| Browse is opened or its tag filter changes | Every `.md` whose mtime moved | The tag filter |

A file edited in another terminal is therefore seen the next time a tree screen
is opened, MD mode is left, or anything compiles — never while the app sits
still on a screen.

## 5. The marker and the warnings list

**Settled with the dev:** a marker in both trees, the list in Inspect Tree's
preview pane, and no count anywhere else. A file edited through the app gets
exactly the same treatment, with no extra notice — a warning belongs to the
file, not to what wrote it.

- **The marker.** A file leaf whose file has warnings is labelled `<stem> ⚠`,
  the `⚠` dim, the stem the `literal()` `Text` it already is — in **both**
  Inspect Tree and Entry. Nothing else about either tree changes; a marked file
  opens, previews, compiles, renames and deletes exactly as a clean one.
- **The list.** Inspect Tree's preview pane heads the file with its warnings, in
  **MD mode only** (changed 2026-10-02 after the dev hand-tested: in PDF mode the
  block competes with the rendered page for the pane, and the page is the point
  of that mode — see *Found while implementing*):

  ```
  ⚠ 3 warnings
  line 12: unrecognized line
      | word | gloss |
  line 14: extra column(s) never rendered: junk
      你	ni3	you	junk
  line 20: category 'Fruits' appears more than once
      ## Fruits
  ```

  Singular for one (`⚠ 1 warning`); each warning's raw line indented beneath it;
  a file-level warning shown without a line number; capped at ten warnings with
  `… and N more` as the last line. The whole block is `literal()` — it quotes
  the file.
- The block is hidden for a directory, the root, a file with no warnings, and in
  PDF mode whatever the file holds. The marker stays in both modes, so a warned
  file is still flagged in PDF mode; its list is one `tab` away. It is not
  focusable and binds no keys.
- **No count anywhere else**: not on the notebook menu, the landing menu or a
  footer. No screen parses the tree to show a number.

## 6. Compile and `idiomas compile`

- `Render` gains `warnings`, filled by `render_source` from the `parse()` call
  it already makes.
- `compile_all` appends one `CompileWarning` per parse warning, its message
  `line N: <message>` with the offending line indented beneath it — for **every** file it looks at, rebuilt or skipped (M3) —
  alongside the existing unsupported-pinyin warning.
- `compile_summary` groups warnings by source: one path line, then each
  warning's message indented beneath it, every line indented (matching the
  *Failed:* block, which it does not match today).
- `idiomas compile` prints the same grouping to stderr and **does not** change
  its exit status. A warned file still compiles and still counts as compiled.

## Found while implementing (2026-10-02)

Each is a consequence of §2's rule rather than a new decision, and each is in
the code and its tests.

| Finding | What it changes |
| --- | --- |
| **An unquoted multi-word tag is lossy**, so it is reported — not lossless as this spec first had it | `#C1 exam` is `shlex`-split into `C1` and `exam`: one tag silently becomes two. It falls under "a token that is not a `#tag`". The *Not reported* row now covers only the reverse — quoting the writer would not have used. |
| **A tab-indented entry row now reports twice** | M1 settled that `\t你\tni3\tyou` reads as a row with an empty first field, because a leading tab cannot be both indentation and an empty field. By §2 that row has no word *and* a fourth column holding `you`, and both are reported. The deck is M1's, unchanged; three of its tests now assert the warnings beside it. |
| **`parser._parse_tags_line` is renamed `_split_tags_line`** | It returns the line's `shlex` tokens with their `#` intact, since the caller now has to tell a `#tag` from a word that never had one. Stripping stayed at the one call site. |
| **`store.walk`'s callers needed no change** | Both already pass the notebook's tree root as `root`, so threading it through the recursion was internal. |
| **Inspect Tree's cursor is restored through the tree's lines, not its nodes** | A tree just rebuilt has no line numbers yet, and `move_cursor` works off them. Reading the lines is what assigns them, so `node_for` walks `get_node_at_line`; doing it after a refresh instead made the behaviour depend on the message loop. |
| **The preview's image is sized to a new `#preview-body`** | As the spec anticipated. The container holds the message and the image; the warnings block sits above it and takes its height from the panel. |
| **MD mode opens `nvim` with `noexpandtab`** (dev, hand-testing, 2026-10-02) | A row's columns are separated by real tabs, and an `nvim` with `expandtab` on writes spaces when the dev presses Tab, so a hand-fixed row stayed an `unrecognized line`. Spaces cannot be read back as columns (a tab can come out as one space, and translations hold spaces), so the parser is unchanged and the editor is told to write what the format needs: the app runs `nvim -c "set noexpandtab" <file>`. Applies to the buffer opened from Inspect Tree only; the dev's own config is not touched. |
| **The warnings block is MD-mode only** (dev, hand-testing, 2026-10-02) | The first cut showed it in both modes. In PDF mode it shrank and displaced the rendered page, which is what that mode is for. `_update_preview` now shows the block only when `mode == "md"`; the `⚠` marker in both trees is unchanged, and toggling mode shows or hides the block for the file under the cursor. |
| **A Compile warning is two lines, not one** | `line 5: extra column(s) never rendered: junk: 苹果…` is unreadable, because a message can end in a colon of its own. The raw line goes on its own indented line instead — the pane's shape — which both surfaces already indent line by line. |
| **A new file is never marked** | Inspect Tree's `m` writes `# <name>` into it, so the missing-header check cannot fire on a file the app just created. |

## Out of scope

- **Any live detection** — no watcher, no polling, no re-read on screen resume.
  The dev's call (§4).
- **A tree-wide or menu-level warning count.** The dev's call (§5).
- **Changing what `parse()` keeps.** The checks of §2 add warnings only: every
  file's deck, tags and PDF come out exactly as they do today, so no existing
  PDF changes and nothing can regress. Dropping a non-`#` tag token or an extra
  column would change decks, Browse's tag list and compiled output for files
  that parse today — a scope jump for the sprint's last milestone, and it would
  make the app a format enforcer rather than a reporter.
- **Refusing or repairing a bad line.** Warnings are information. The app never
  rewrites a line it did not understand, and never withholds a PDF for one.
- **Normalizing a file on demand.** A conforming-but-untidy file is rewritten
  into §1's shape by the next in-app write and nothing else; there is no
  "tidy this file" action.
- **Browse.** It lists PDFs and has no file-level surface to mark; the two tree
  screens and Compile cover every file.
- **Editing or deleting an existing entry in the app** — the sprint's standing
  Postponed item. Fixing a warned line still means `nvim`.
